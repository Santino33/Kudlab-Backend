# RF-008 (V3, propuesta): evidencia y control de consentimiento

**Resultado:** evidencia accesible solo a autorizados y verificación en servidor antes de activación y cada nueva tarea. [V3 RF-008](../../../../original/requisitos_V3.xlsx), [D ADR-03, §2.2 pp. 5–6, §6.2 p. 14](../../../../original/DESCRIPCI%C3%93N%20DE%20DISE%C3%91O%20DE%20SOFTWARE.docx.pdf), [CU estudiantes](../../../../original/DIAGRAMAS-ANALISIS/DIAGRAMAS/02-casos-de-uso/02-cu-gestion-estudiantes/02-cu-gestion-estudiantes.png). Actor: administrador gestiona evidencia en A §7.1; acudiente firma externamente, no inicia sesión.

**Entradas exigidas por V3:** evidencia, fecha de recepción, estado, fecha de vigencia/revocación cuando aplique y responsable del registro; tipos concretos de estado son **conflictivos** (`APROBADO/PENDIENTE/RECHAZADO` ERD vs `VIGENTE` D). **Flujo:** registrar evidencia/metadatos → restringir consulta → validar vigencia en servidor al activar participante y antes de iniciar actividad → permitir o bloquear → registrar cambios; revocación/vencimiento impide nuevas ejecuciones. D §6 propone R2 privado para archivo, PostgreSQL para clave/hash/estado y URL prefirmada ([PUML R2](../../../../original/C4/UML/integracionCloudflare.puml)); no es contrato de upload. **Verificación:** pendiente/sin evidencia bloquea activación e inicio; aprobado válido habilita; revocado impide *nuevas* ejecuciones; operador no autorizado no obtiene archivo; cambio trazable. Probar expiración/revocación entre asignación e inicio. Pendiente: formatos, retención, consecuencias para datos previos y cardinalidad 1:1 del [ERD](../domain-model.md).
