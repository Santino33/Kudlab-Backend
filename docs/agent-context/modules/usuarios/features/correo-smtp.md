# Propuesta de feature: habilitar entrega de correos por SMTP

**Resultado:** dejar operativos en un entorno del piloto los correos de [invitación](cuentas.md), verificación de cambio de dirección y [recuperación de acceso](autenticacion.md), para que el personal pueda activar y recuperar su cuenta. Esta solicitud define la necesidad de configuración y verificación; **no es un RF adicional aprobado en V3**.

**Situación actual:** `src/modules/usuarios/invitations.mailer.ts` ya envía por SMTP mediante Nodemailer; `src/config/env.ts` exige host, puerto, usuario, contraseña y remitente cuando se usa ese modo. `.env.example` documenta esos valores y las URL de invitación y recuperación. Las pruebas capturan mensajes sin enviarlos. Falta aportar credenciales de un proveedor autorizado, configurar las URL reales y comprobar la entrega de extremo a extremo en el entorno del piloto; no hace falta construir otro servicio de correo.

**Flujo y verificación:**

1. El operador configura fuera del repositorio los datos SMTP y un remitente válido, junto con los destinos HTTPS de invitación y recuperación de la aplicación web. Si falta configuración necesaria, la aplicación no debe aparentar que puede enviar correos.
2. Un administrador autorizado invita a un docente: se conserva la cuenta pendiente y la invitación ya registradas; el envío confirmado por el servidor SMTP se refleja en el estado de entrega. Si SMTP rechaza o no confirma el mensaje, se informa el fallo sin declarar la cuenta activa ni afirmar entrega exitosa. Verificar además qué puede consultar el administrador para gestionar una invitación no recibida antes de prometer reenvíos.
3. Al solicitar cambiar el correo de una cuenta activa, el mensaje llega a la nueva dirección; la dirección anterior sigue vigente hasta la confirmación. Ante fallo de entrega, no se confirma el cambio ni se informa falsamente que el correo nuevo ya está activo.
4. En recuperación, la solicitud ofrece la misma respuesta pública para correo existente o desconocido; el mensaje solo se intenta para una cuenta elegible. Un fallo SMTP no debe revelar si la cuenta existe ni activar acceso, y una confirmación válida sigue invalidando las sesiones anteriores.
5. Probar en el entorno previsto invitación, confirmación de correo y recuperación usando buzones de prueba, incluidas fallas de conexión, rechazo del proveedor y configuración incompleta. Confirmación de SMTP significa **aceptación por el servidor de correo**, no garantía de lectura o llegada a la bandeja de entrada; verificar recepción con buzones de prueba antes del piloto. No registrar contraseñas SMTP ni enlaces de un solo uso en logs o documentación.

**Dependencias/decisiones:** obtener cuenta remitente y credenciales del operador; disponer de páginas de aceptación y recuperación en el frontend; acordar cómo reintentar o reenviar verificaciones que no llegan **solo si la prueba real demuestra esa necesidad**. Mantener vencimiento y uso único de los enlaces según las especificaciones ya acordadas. No incluir notificaciones generales, plantillas configurables ni nuevas cuentas de usuario.

**Trazabilidad:** `specs/001-gestionar-cuentas-roles/spec.md`, sección Assumptions, consigna la invitación por correo como decisión del responsable; `specs/003-autenticar-usuarios/spec.md`, sección Assumptions, documenta la recuperación confirmada para esa iteración. `docs/original/requisitos_V3.xlsx`, hoja «RF corregidos», filas 2–4 (RF-001…003), estado «Propuesto - corregido para validación», cubre cuentas y autenticación **sin exigir proveedor SMTP específico**. `docs/original/3 ANALISIS DEL PROYECTO.docx.pdf`, CU01-S1 y CU02, pp. 27–31, describe alta y acceso, sin configurar correo. SMTP es una decisión de integración del proyecto actual, no una obligación heredada del análisis original.
