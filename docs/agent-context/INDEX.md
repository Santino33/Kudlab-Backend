# Contexto técnico para agentes

Esta capa orienta el trabajo sobre **este backend**, conservando la trazabilidad de `docs/original/`. No equivale a `spec.md`, `plan.md` ni `tasks.md`. Los profesores son los únicos usuarios humanos de este proyecto; ADMIN/TEACHER distinguen sus permisos. Los estudiantes interactúan con **otro servicio de juegos**, no con una cuenta de este backend. La API gestiona participantes, tareas/asignaciones y los registros acordados con ese servicio; no implementa las mecánicas ni pantallas del juego.

## Cómo empezar sin conocer el proyecto

1. Leer [alcance y glosario](project-context.md) y [responsabilidades](module-boundaries.md).
2. Consultar [arquitectura y estado actual](architecture-summary.md) y [guía de implementación](implementation-guide.md): qué existe, dónde modificarlo y cómo probarlo.
3. Leer el resumen del módulo, su modelo y la feature afectada. Las fichas TG explican el contexto del productor externo, no ordenan desarrollar juegos aquí.
4. Comprobar [decisiones](decisions.md) y [bloqueos](unresolved-issues.md). Para Tareas/Evolución leer además [integración con juegos](games-integration.md).
5. Verificar el fragmento original pertinente antes de fijar una regla; seguir [fuentes y acceso desde worktrees](sources.md). Contrastar las funcionalidades existentes con código, contratos y pruebas enlazados, sin sobrescribirlas con diseños antiguos.

**Estados documentales:** `alcance confirmado` = aclaración explícita del responsable; `implementado` = observado en esta revisión de código, no certificación de pruebas; `diseño original` = propuesta de las fuentes; `recomendación` = organización sugerida, no carpeta/endpoint existente; `pendiente` = requiere decisión antes de implementar la parte afectada. Para RF/RNF indicar **fuente y versión**: los IDs de A, D y V3 no son intercambiables. La constitución vigente se consulta en [su archivo](../../.specify/memory/constitution.md); este contexto no la modifica.
